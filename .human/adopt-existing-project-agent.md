# Внедрение и обновление Spec Drive в существующем проекте

Прочитай AGENTS.md и BOOT. Работай сначала с областью текущего запроса. Само наличие старых документов не требует полной переписи проекта.

## Существующий код без канона

Изучи README, релевантные docs/ADR, код, тесты и реальные команды запуска. Отделяй наблюдения, предположения и согласованные требования.
Заполни main, карту продукта и техническую карту подтверждёнными сведениями. Создай нужные draft PROP/FEAT/INFRA, сохраняя реальные границы и сценарии; согласуй существенные решения до active и реализации.
Не переписывай код ради красивой структуры и не выдавай известный баг за желаемый контракт.
Для полной адаптации большого проекта сначала определи области и приоритеты; применяй запрос пользователя к согласованному объёму, сохраняя возможность продолжения через WI/checkpoint.

## Переход со Spec Drive 1

Установщик обновляет узнаваемые неизменённые протоколы, но сохраняет проектные спеки и оперативные записи. Он не объявляет старые задачи завершёнными и не переносит их автоматически.

Перед изменением конкретной legacy FEAT/INFRA строки:
1. Найди соответствующую спеку, BOARD и checkpoint; сохрани текущий результат, owner, зависимости и незавершённые шаги.
2. Создай WI со свободным ID. Перенеси туда результат текущего прохода, in/out и критерии; спека остаётся описанием продукта с прежним ID/адресом.
3. Замени только эту строку BOARD на ссылку WI, сохранив статус/owner. Если работа не закончена и нужна пауза, преобразуй только её WAL-секцию в checkpoint WI с Next.
4. Добавь owning spec в SPEC-MAP. Legacy без status считается active до проверки; при содержательной правке явно укажи честный lifecycle.
5. Старые `.A/.B` сохраняют адреса. Уточняй текущий governing canon при работе с областью; не переименовывай весь архив.
6. Старые Done/Completed можно оставить как историю. Новые завершения оформляй через WI Result и архив, без новых Completed записей WAL.

Если старый PROP-000 или другой документ описывает сам workflow и дублирует правила v1 (FEAT как задачу, обязательный WAL при старте), обнови эти служебные положения под v2 до зависимой работы. Сохрани доменные ограничения продукта; не объявляй весь исторический документ недействующим только из-за устаревшей маршрутизации.

При преобразовании активной задачи не теряй acceptance и не смягчай их. Для старого Done без evidence не выдумывай задним числом проверки.

## Конфликты установщика

Если изменён служебный файл, обновление останавливается до записи. Сравни текущий файл с новой версией из дистрибутива и перенеси проектные ограничения отдельно от общих правил. После осмысленного согласования повтори установку; не применяй force поверх незнакомых инструкций.
При Prist-managed этот standalone installer останавливается. Для переключения источника состояния нужен отдельный перенос и проверка; недоступность сервиса не означает разрешение создать локальный BOARD/WAL.
