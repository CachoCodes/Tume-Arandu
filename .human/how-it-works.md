# Как работать со Spec Drive 2

Spec Drive сохраняет замысел продукта и помогает агенту находить нужный контекст между сессиями.

## Что где живёт

| Вопрос | Документ |
|---|---|
| Как должно работать сейчас? | PROP / FEAT / INFRA в common/ и modules/ |
| Где искать нужную область? | SPEC-MAP.md; пути к коду и проверкам в common/structure.md |
| Какой результат делаем этим проходом? | specs/work/WI-NNN.md |
| Кто делает и каков статус? | BOARD.md |
| На чём остановились и что делать дальше? | WAL.md, только для незавершённой работы |
| Какой компромисс сознательно оставили? | TECHDEBT.md |

Спецификация — текущее поведение; WI — изменение. Например, FEAT описывает авторизацию, разные WI реализуют email-вход, исправляют продление сессии и добавляют Google-вход.

## Как ставить задачи

Можно обычным языком: «Исправь повторную отправку приглашения». Агент найдёт область через карту, спеку и @spec. Точный spec-адрес или WI ускоряет вход, но не обязателен.
Для узкого исправления по ясному канону агент меняет код и проверяет результат без служебных записей. Для самостоятельного результата, риска, зависимости или продолжения создаёт WI и строку BOARD.
При новом поведении той же ответственности обновляется существующая спека. Новая самостоятельная ответственность получает новую спеку. История остаётся в Git; новая волна реализации не требует `.A/.B`.

## Как принимать результат

Смотри Result WI: каждый AC связан с выполненной проверкой, командой или артефактом. Для UI нужна проверка работающего сценария в браузере; скриншот подтверждает внешний вид, но не весь функционал.
Done означает, что обязательные критерии проверены. Невыполненная обязательная проверка оставляет работу незавершённой. Lint проверяет структуру, а не истинность заявления агента.
WAL появляется только при паузе, handoff или блокере. В нём есть достигнутое состояние и точный Next; после Done checkpoint удаляется.

## Начало

Установщик уже создаёт каркас и локальную identity `specs/.me` из имени учётной записи. При необходимости поправь её; она игнорируется Git.
Новый проект: [start-project-instruction.md](start-project-instruction.md).
Существующий проект/обновление v1: [adopt-existing-project-agent.md](adopt-existing-project-agent.md).
`specs/examples/` содержит образцы, которые агент адаптирует к реальным требованиям. В пустом проекте нет фиктивных активных фич, долгов и задач.

## Проверки

Из корня проекта: `python3 tools/spec-lint.py` (Windows: `py -3 tools/spec-lint.py`). Нужен Python 3.9+, сторонних библиотек нет. Сам установщик использует штатные средства ОС и Python не требует.
Можно добавить эту команду в существующий CI. Не нужно создавать новый стек CI ради workflow.
Ошибки ссылок, duplicate ID, lifecycle и заполненности Done блокируют lint; legacy-документы дают предупреждения для постепенного обновления.

## Параллельная работа

Каждый исполнитель имеет identity, а один координатор владеет оперативными записями одного WI. Проверяй пересечения кода и контрактов; разные секции WAL не гарантируют отсутствие merge-конфликтов. При необходимости используй отдельные worktree и явные зависимости WI.

## Повторная установка

Установщик сохраняет README, канон, BOARD/WAL, .me и ROADMAP. Неизменённые служебные файлы обновляет, резервные копии заменённых файлов сохраняет в `.spec-drive/`. Изменённый пользователем служебный файл вызывает конфликт до применения обновления; точный путь показывается в результате.
Собственные AGENTS/CLAUDE сохраняются с добавлением одного блока маршрутизации. Неизвестные старые BOOT/Prist instructions требуют согласования, чтобы не активировать два противоречащих workflow.
Оперативное состояние здесь хранится в Git-файлах. Для перехода в Prist нужен отдельный согласованный перенос; установщик не подключает сервис и не создаёт дубли его состояния.
