# BOOT — Spec Drive 2

## Источник состояния

Этот workflow работает автономно: канон и оперативное состояние лежат в репозитории.
Если `.prist/workflow.json` явно задаёт `prist-managed`, используй установленный Prist workflow; не веди локальные WI/BOARD/WAL/TECHDEBT параллельно сервису. Не меняй режим по доступности сети.

## Найди контекст

- Указан WI: открой его файл (или архив), строку BOARD и только его checkpoint WAL, если он есть.
- Обычный запрос: найди область через `specs/SPEC-MAP.md`, `specs/common/structure.md`, заголовки/якоря спек и `@spec` в коде и тестах. Расширяй чтение по реальным зависимостям.
- Пустой проект: прочитай `.human/start-project-instruction.md`. Существующий проект без канона: `.human/adopt-existing-project-agent.md`.
- Старые FEAT/INFRA в BOARD: перед оперативными изменениями мигрируй нужную запись по `.human/adopt-existing-project-agent.md`; не переписывай всю историю.

## Выбери маршрут

| Запрос | Действие и обязательное чтение |
|---|---|
| Вопрос / анализ | Только чтение; без WI, `.me`, BOARD и WAL mutations. |
| Узкий фикс по ясному active-канону, без отдельного риска, зависимости, координации или продолжения | Код + релевантная проверка; без WI/BOARD/WAL. Если scope вырос, перейди к отслеживаемой работе. |
| Работа с собственным результатом, несколькими существенными шагами, риском, зависимостью или продолжением | `WORK-ITEM-PROTOCOL.md` + `BOARD-PROTOCOL.md`; создай/возобнови WI перед реализацией. |
| Новый или изменяемый канон | `SPEC-PROTOCOL.md`; при новом/глубоко переписываемом документе также `SPEC-AUTHORING-PROTOCOL.md`. Для отслеживаемой работы заведи WI до authoring. |
| Пауза, передача, блокер, значимый деструктивный шаг | `WAL-PROTOCOL.md`; сохрани проверенное состояние и ближайший шаг. |
| Осознанный долг вне acceptance | `TECHDEBT-PROTOCOL.md`. |

Протоколы из таблицы лежат в `specs/protocols/`. Перед claim или изменением оперативных файлов прочитай `specs/.me`. Если его нет, используй подтверждённую identity пользователя/окружения для создания из `.me.template`; уточняй только неоднозначную identity. Для чтения и узкого фикса `.me` не нужен.

## Выполнение и завершение

Сообщи кратко область и ожидаемый результат. Пользовательский запрос задаёт scope; соседние ошибки не расширяют его автоматически.
Сверь актуальную спеку и реальный код. Для материально изменённых точек ответственности и прямых contract tests оставляй полный `@spec spec://...#anchor` на действующий канон.
Не реализуй заведомо опасное или неоднозначное поведение вслепую: следуй правилам конфликта в `SPEC-PROTOCOL.md`.
Один WI — один проверяемый результат; коммитов может быть несколько. Коммит/публикация выполняются в рамках указаний пользователя и проекта.
Выполни подходящие acceptance-проверки после последней относящейся к ним правки; для веб-UI проверь затронутый сценарий в браузере, состояния ошибок и доступность по scope.
Запусти `python3 tools/spec-lint.py` (Windows: `py -3 tools/spec-lint.py`), когда менялись канон, WI/BOARD/WAL или `@spec`. Это структурная проверка, не замена тестам поведения.
При Done запиши Result/evidence в WI, обнови BOARD, удали существующий checkpoint; при паузе сохрани checkpoint. Для завершённого узкого фикса достаточно результата и проверки в ответе.
