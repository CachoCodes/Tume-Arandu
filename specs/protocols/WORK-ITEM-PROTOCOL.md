# WORK-ITEM-PROTOCOL

## Когда нужен WI

Отдельный проверяемый результат, несколько существенных шагов, риск, зависимость, координация, блокер или продолжение между сессиями требуют `WI-NNN`.
Узкий фикс по ясному канону без этих признаков проходит без оперативных записей.
Один результат может затрагивать несколько спек. Несколько независимых результатов разделяются на связанные WI.

## Файл задачи

Создавай `specs/work/WI-NNN-short-slug.md` по образцу `specs/examples/WI-000-example.md`.
ID уникален во всех активных и архивных WI и не переиспользуется.
Обязательные секции: Outcome, Scope (in/out), Specs, Acceptance, Dependencies, Risks, Result.
Поле `Canon action: none|direct-edit|new-spec|supersede` описывает действие с каноном.
В Specs перечисли точные governing/constraint/affected адреса. При new-spec до появления файла укажи планируемый путь без действующей ссылки; перед зависимой реализацией обнови его на active governing anchor.
Acceptance оформляется строками `- AC-1: наблюдаемый критерий` с уникальными ID. Отдельные поля status/owner в WI не нужны — они в BOARD.

## Start и scope

Перед реализацией создай полный WI и строку BOARD с owner. При возобновлении прочитай Result/незавершённый checkpoint и перепроверь текущее состояние.
Новый запрос расширяет WI только при сохранении того же атомарного результата; независимая работа и продолжение закрытого WI получают новый связанный WI.
Не ослабляй согласованные критерии ради завершения задачи. Не добавляй scope из соседних ошибок без основания в запросе.
При параллельной работе сверяй пересечения файлов и контрактов, используй отдельные worktree при необходимости. Один координатор обновляет WI/BOARD/checkpoint/result одной задачи; запись своего handle в WAL не защищает код от конфликтов.

## Done и evidence

В Result запиши итог, REVIEW/техдолг и таблицу:

| Criterion | Check / evidence | Result |
|---|---|---|
| AC-1 | точная команда или путь к артефакту / запись выполненного ручного сценария | passed |

Для каждого AC должна быть реальная подходящая проверка. Общая команда может проверять несколько AC, если это действительно её контракт.
Проверки выполняются после последней относящейся к ним правки. Запиши дату, Git commit при наличии и состояние working tree; после последующей правки повтори затронутые проверки. Не приписывай новым изменениям старый зелёный запуск.
Для UI evidence включает проверку работающего сценария; один скриншот не подтверждает поведение. Для недоступной обязательной проверки укажи причину, сохрани WI незавершённым.
Когда критерии выполнены, перенеси файл в `specs/work/archive/YYYY/`, исправь ссылку BOARD, поставь Done и убери checkpoint. Не создавай запись Completed в WAL.
Структурный lint проверяет заполненность evidence; его истинность подтверждают выполненные команды, артефакты и review.
