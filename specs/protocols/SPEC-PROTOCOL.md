# SPEC-PROTOCOL

## Приоритет и ответственность {#priority}

Решение пользователя → актуальная спецификация → тесты → код.
Спецификация описывает текущее поведение, контракт или инвариант. Задача `WI-NNN` описывает один проход изменения. Owner, status и прогресс реализации не живут в спеке.
`PROP` — устройство и инварианты; `FEAT` — продуктовая возможность; `INFRA` — эксплуатационный контур.

## Формат и lifecycle {#lifecycle}

Канон хранится в `specs/common/` и `specs/modules/<area>/`.
Имя: `TYPE-NNN-short-slug.md`; номер уникален для типа во всём spec-space, включая исторические документы. Не переиспользуй ID.
Каждая спека имеет явный `{#root}`, стабильные `{#scope}`, `{#acceptance}` и необходимые смысловые якоря, блок простыми словами, scope, конкретные правила, acceptance и историю изменений.
Адрес: `spec://modules/account/FEAT-010-login#session.refresh` (без `.md`).

YAML в начале: `status: draft|active|superseded|retired` между строками `---`.
- `draft`: предложение, не governing canon для зависимой реализации.
- `active`: действующее требование; не утверждение, что код уже готов.
- `superseded`: документ заменён; сохраняй путь и взаимные `Supersedes` / `Superseded by` ссылки.
- `retired`: область выведена без замены; сохраняй историю и ID.
Legacy-спека без статуса временно считается active; уточни статус при следующей содержательной правке. `specs/examples/` — учебные образцы, не канон.

## Изменения {#change-model}

- Та же ответственность и согласованное изменение поведения: direct edit + история изменений. Реализация при необходимости получает WI.
- Самостоятельная новая ответственность: новая спека и новый ID.
- Полная замена/разделение/объединение документа: supersession с новым ID и взаимными ссылками.
- Старое и новое поведение одновременно нужны: явно опиши условия применимости обоих active-контрактов и переход/откат.
- Новая волна реализации сама по себе создаёт WI, а не `.A/.B`. Существующие буквенные ID и ссылки сохраняются для совместимости.
Исторические срезы сохраняются Git-коммитами, tags или release artifacts по правилам проекта.

## Карта и связи {#map}

Регистрируй каждый канонический документ в `SPEC-MAP.md`: область, точный адрес, lifecycle. Обновляй `common/structure.md` только при изменении технических границ или путей.
При реальной связи используй Related, Depends on, Supersedes, Superseded by, See also с точными адресами. Governing — владелец поведения; constraint — применимое ограничение; affected — то, что изменение затрагивает. Не объявляй все соседние спеки governing.

## Конфликт {#conflict}

Код расходится с ясным active-каноном: воспроизведи проблему, исправь код и тесты, `Canon action: none`.
Пользователь изменил требование: сначала обнови owning spec, затем реализацию.
Обычный спор о способе реализации: следуй канону, при необходимости оставь `<!-- REVIEW: вопрос и причина -->` и сообщи о нём.
Противоречивый контракт, неразрешённое продуктовое решение или известный риск потери данных, нарушения безопасности, денег либо основного сценария: не реализуй опасную часть вслепую; опиши конкретный конфликт и запроси необходимое решение. Продолжай независимую разрешённую работу.

## Traceability {#traceability}

На новом или существенно изменённом файле, handler/service, крупном UI-компоненте, worker, migration и прямом contract test ставь `@spec` с полным адресом и якорем active-канона.
Мелкие helpers наследуют ближайшую ответственность. Не размечай каждую строку.
При изменении ответственности обновляй маркеры и проверь ссылки через `tools/spec-lint.py`.
